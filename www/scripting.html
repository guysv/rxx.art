rxx embeds a Rune scripting engine that lets you extend the editor with plugins. Plugins are scripts that can draw overlays, register custom commands, extend GPU pipelines, and react to user input. This guide walks through the core ideas; the API reference has the full surface.

overview

A plugin is a <name>.rune file in the plugin directory, or a <name>/<name>.rune package whose directory carries its assets (WGSL shaders, PNG icons). The plugin directory defaults to the OS config dir's plugins/ subdirectory; point rxx elsewhere with --plugin-dir <path>. Plugins load in lexicographic order, and hot-reload when their file changes — no restart.

Every plugin exports pub fn init(rx). It runs once at load and returns the plugin's state value — usually a map (#{ ... }). That value is handed back as the first argument of every other hook, command handler, and export, so plugin state is explicit rather than global.

A script error or GPU validation error disables only the offending plugin and posts one message — other plugins keep running, and the frame survives. During development, watch the message line.

Let's start with a small but genuinely useful plugin: a classic vim-style 'current mode' indicator. It defines two hooks — init to set up state, and draw to paint the overlay each frame. 

// mode-vis.rune - current mode indicator

const TEXT_X = 10.0;
const TEXT_Y = 46.0;

pub fn init(rx) {
    // no state needed; return an empty map
    #{}
}

pub fn draw(state, rx) {
    let mode = rx.mode();
    let label = `-- ${mode.to_uppercase()} --`;

    if mode == "normal" {
        rx.draw_text(label, TEXT_X, TEXT_Y, rx::rgb(255, 255, 255));
    } else if mode.starts_with("visual") {
        rx.draw_text(label, TEXT_X, TEXT_Y, rx::rgb(0xff, 0x33, 0x66));
    } else if mode == "command" {
        // command mode is skipped
    } else {
        // script and other modes
        rx.draw_text(label, TEXT_X, TEXT_Y, rx::rgb(0xff, 0x33, 0x66));
    }
}

The draw(state, rx) hook is called every frame, on the UI tier — this is the only place rx.draw_text and rx.draw_line are live. It reads the current mode with rx.mode(), formats a label, and paints it at a fixed position in a color that depends on the mode. UI coordinates are y-down, origin top-left.

registering commands

From init you register commands the user can invoke from the command line. rx.register_command(name, sig, help, handler) takes a name, a typed parameter signature, a help string, and a handler function. The handler is called as handler(state, rx, args), where args holds the parsed, typed arguments. 

pub fn init(rx) {
    rx.register_command("greet", ["str"], "Say hello", greet);
    #{ count: 0 }
}

pub fn greet(state, rx, args) {
    state.count += 1;
    rx.message(`hello ${args[0]} (${state.count})`);
}

Running :greet world posts hello world (1) to the message line, then (2), and so on — the count lives in the plugin state that init returned. The signature is a list of type tags: "int", "float", "str", "color", "bool", with a trailing ? for an optional parameter. Use register_command_repeating for a command that repeats while its bound key is held.

other events

Plugins react to view lifecycle, frame updates, and mouse input through optional hooks — define a pub fn with the right name and signature and rxx calls it.

view lifecycle

view_added(state, rx, id) and view_removed(state, rx, id) fire when the user opens or closes a view. Use them to keep per-view state in sync — e.g. drop an entry from a map keyed by view id so you don't hold stale references.

mouse input

mouse_input(state, rx, button, input) delivers button events: button is "left", "right", or "middle"; input is "pressed" or "released". The hook carries no coordinates — read the cursor with rx.cursor() (session coordinates), or track it from cursor_moved(state, rx, x, y), which receives window-logical coordinates (rx.session_coords(x, y) converts them). 

pub fn cursor_moved(state, rx, x, y) {
    state.mx = x;
    state.my = y;
}

pub fn mouse_input(state, rx, button, input) {
    if button != "left" || input != "pressed" {
        return;
    }
    // hit-test against state.mx / state.my, then act
}

custom script modes

To build a tool that takes over the canvas — rotate a selection by dragging, say — enter a script mode. Any name passed to rx.switch_mode(name) that isn't a builtin enters a script mode: builtin input handling goes inert, escape exits, and your plugin drives everything through its hooks and bindings.

The command line is not reachable from a script mode, so you bind keys to your commands in init with rx.bind(mode, mapping) using :map syntax. The switch_mode(state, rx) hook fires on mode edges — query rx.mode() (and rx.prev_mode()) to detect leaving your mode and clean up. 

const ROTATION_MODE = "visual (rotation)";

pub fn init(rx) {
    rx.register_command("selection/rotate", [], "Rotate the selection", selection_rotate);
    rx.register_command("rotate/apply", [], "Stamp the transformed selection", apply);

    // the command line is inert in a script mode, so bind keys here
    rx.bind(ROTATION_MODE, "<return> :rotate/apply");
    rx.bind(ROTATION_MODE, "'e' :rotate/add 15");
    rx.bind(ROTATION_MODE, "'q' :rotate/add -15");

    #{ in_progress: false }
}

pub fn selection_rotate(state, rx, args) {
    if rx.selection().is_some() {
        state.in_progress = true;
        rx.switch_mode(ROTATION_MODE);
    }
}

pub fn switch_mode(state, rx) {
    // fired on mode edges; clean up when we've left our mode
    let mode = rx.mode();
    if state.in_progress && mode != ROTATION_MODE && mode != "command" {
        state.in_progress = false;
        rx.damage_view(rx.active_view_id());
    }
}

While in the mode, only your plugin's mouse_input and cursor_moved hooks see input. Track the drag, compute an angle from the cursor relative to a pivot, and preview the result in the view's staging texture from shade (below). On :rotate/apply you stamp it into the view as a recorded, undoable edit. The full implementation ships as the rotate-scale sample plugin.

GPU pipeline

For custom GPU work, plugins define shade(state, rx, encoder) and render(state, rx, pass). shade runs first, with the frame's command encoder, before screen composition — record render or compute passes onto script textures, view layers, or a view's staging overlay. render runs on the live screen pass, for screen-space drawing.

Resources are created from init (or a command handler): rx.create_shader(wgsl) compiles WGSL, rx.create_render_pipeline(shader, vs, fs, textures) builds a pipeline (sprite vertex layout, alpha blending, textures = 0–3 texture groups), and rx.create_texture(w, h) / rx.read_png(path) supply texture data. Bind groups and sprite vertices come from the rx.create_*_bind_group and rx.create_sprite_vertices* helpers.

shade(state, rx, encoder)

Begin a pass on the encoder (begin_render_pass, begin_view_pass, begin_staging_pass, or begin_compute_pass), then set pipeline, bind groups, and vertex buffer and call draw. One pass is open at a time; beginning a new one ends its predecessor. Use the staging overlay for an uncommitted preview (cleared every frame), or a view pass followed by rx.touch_view(id) to record an undoable edit. 

pub fn shade(state, rx, encoder) {
    if !state.in_progress {
        return;
    }
    let view = active_view(state, rx);
    let dst = rx::rect(state.bx1, state.by1, state.bx2, state.by2);

    let tbg = rx.create_transform_bind_group(view.width, view.height, state.transform).unwrap();
    let sbg = rx.create_texture_bind_group(state.clipboard).unwrap();
    let verts = rx.create_sprite_vertices(state.clipboard, dst, rx::rgb(255, 255, 255), 0.9).unwrap();

    // staging overlay: a live preview, cleared each frame
    let pass = encoder.begin_staging_pass("rotate-scale", state.active_view_id, "load").unwrap();
    pass.set_pipeline(state.nearest).unwrap();
    pass.set_bind_group(0, tbg).unwrap();
    pass.set_bind_group(1, sbg).unwrap();
    pass.set_vertex_buffer(0, verts).unwrap();
    pass.draw(verts.count(), 1).unwrap();
}

render(state, rx, pass)

render receives a pass over the live screen, sized to rx.screen_size() — build screen orthos against it. Draw screen-space sprites here: an overlay anchored to the window, a HUD, an icon strip. The layer-status sample plugin uses it to draw a per-layer visibility column at the screen's edge. 

pub fn render(state, rx, pass) {
    let (sw, sh) = rx.screen_size();
    let tbg = rx.create_transform_bind_group(sw, sh, rx::mat4_identity()).unwrap();
    let sbg = rx.create_texture_bind_group(state.icons).unwrap();
    pass.set_pipeline(state.show).unwrap();
    pass.set_bind_group(0, tbg).unwrap();
    pass.set_bind_group(1, sbg).unwrap();

    let src = rx::rect(0.0, 0.0, 16.0, 16.0);
    let dst = rx::rect(10.0, 10.0, 26.0, 26.0);
    let v = rx.create_sprite_vertices_src(state.icons, src, dst).unwrap();
    pass.set_vertex_buffer(0, v).unwrap();
    pass.draw(v.count(), 1).unwrap();
}

That's the core. For the exhaustive list of functions, types, and the conventions that bite (y-up rects vs y-down bytes, snapshot-vs-live reads, the params-buffer sizing rule), see the API reference — and read the sample plugins under plugins/, which exercise all of it.
